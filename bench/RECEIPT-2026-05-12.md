# Two weeks of TurboQuant on consumer hardware — what landed

**Date:** 2026-05-12
**Stack:** llama.cpp + Qwen 27B q8/turbo4 on RTX 4090; vLLM `feature/turboquant_plus` @ `36fc04825` + Qwen 2.5 (7B / 14B-AWQ / 32B-AWQ) + Mistral 7B on RTX 4090 / WSL2 Ubuntu 24.04
**Scope:** consumer-GPU (24 GiB) + adversarial-retrieval workloads. Not 70B+, not H100, not partial-credit reasoning benchmarks.

## What this is

Curatorial receipt of the work in `sztlink/turboquant-cuda-bench` between 2026-04-28 and 2026-05-12. Not a survey. Not a roadmap. A narrative of what was tested, what survived, and what the limit of the receipt is.

Four findings landed. They are listed in order of how they accumulated, not in order of importance.

---

## Phase 1 — llama.cpp + RTX 4090

### needle 5/5 at 192K context on a single 4090

Qwen 27B (dense) with `q8_0/turbo4` KV-cache config holds the full 192K window on a consumer 24 GiB GPU and retrieves the canonical needle at p05, p25, p50, p75, p95 positions. The 4090 fits, decoding stays usable, KV compression delivers what TurboQuant advertised in its first public claim. **Step one of the consumer-GPU long-context question is settled.**

Receipt: [`bench/needle-retrieval-2026-05-10/`](needle-retrieval-2026-05-10/)

### decoy k=16: a 5/8 ceiling that is not the model's fault

The same Qwen 27B, with a curated 16-chunk retrieval set containing decoys, hits 5/8 on adversarial exact-match. Three handles fail; the model commits to literal `DECOY-####` strings instead of the right SECRET VALUE. This is the first time a coherent failure mode appeared. It is also the first time it became clear the model is not the variable.

Receipt: [`bench/longctx-proxy-hard-2026-05-10/`](longctx-proxy-hard-2026-05-10/)

### policy_splice and rerank both recover to 4/4

Injecting the canonical chunk first as plain text into the user message produces 4/4 across every configuration ever tested here. A reranker over the candidate pool produces 4/4 on most. Both fixes operate upstream of the decoder. The fix is universal because the problem is upstream.

Receipt: [`bench/longctx-decoy-resolution-2026-05-10/`](longctx-decoy-resolution-2026-05-10/)

## Phase 2 — vLLM migration

### Building `feature/turboquant_plus` on consumer hardware in WSL2

A documented from-source recipe for the vLLM TurboQuant fork on Windows 11 + WSL2 Ubuntu 24.04 + RTX 4090. Pip-distributed CUDA toolchain (no system CUDA install), `lib64`/`libcuda.so` symlinks, `MAX_JOBS=4` to avoid OOM, FlashInfer JIT cache pitfalls, V3 attention enablement envs. Tested 2026-05-11. Submitted as PR #1 to `TheTom/vllm-turboquant`.

Receipt: [`bench/vllm-smoke-2026-05-10/BUILD-CUDA.md`](vllm-smoke-2026-05-10/BUILD-CUDA.md) · PR: [TheTom/vllm-turboquant#1](https://github.com/TheTom/vllm-turboquant/pull/1)

### Cross-stack invariance — the first finding worth keeping

Five independent (stack × family × size) configurations — llama.cpp Qwen 27B, vLLM Qwen 2.5-7B, vLLM Qwen 2.5-14B-AWQ, vLLM Qwen 2.5-32B-AWQ, vLLM Mistral 7B — produce the same 5/8 score on the same eight-handle adversarial retrieval workload. The same three handles fail in all five. On at least one handle (`brass-river-index`), the wrong-answer text emitted is **byte-identical** across two different model families on two different inference stacks (`DECOY-0616-1`).

This is not a model property. This is not a stack property. This is not a compression property. It is a property of the relationship between the corpus, the retriever, and the decoder. The model is downstream of the failure.

Receipt: [`bench/vllm-decoy-2026-05-11/`](vllm-decoy-2026-05-11/)

## Phase 3 — FP8 vs TurboQuant K8V4

### Same workload, four FP8 configurations, one TurboQuant configuration

In the public TurboQuant debate of May 2026, Red Hat AI reported FP8 KV-cache as "zero accuracy cost vs BF16" at 70B+ scale on AIME25, GPQA, MATH500, LiveCodeBench-v6, and `openai/mrcr`. The claim is well-supported in that regime. To test where the claim has a boundary, the same dtype matrix was run on Qwen 2.5-7B at 16K context, decoy k=16, on a 4090:

- `auto` (BF16, no compression): **5/8**, three clean decoy commits
- `turboquant_k8v4` (TheTom's preset): **5/8**, byte-identical to BF16
- `fp8` scales=1.0: **0/8**, gibberish across four failure modes (token-mangle, path-leak, loop, format-echo)
- `fp8` + `calculate_kv_scales=True` (on-the-fly): **0/8**, worse than scales=1.0 — loop or collapse on all 8
- `fp8` dataset-calibrated W8A8-KV8 (llmcompressor recipe, ultrachat_200k 512 samples): **0/8 exact-match**, but the model now generates correct templates, correct decoy-commit behavior, and correct system-prompt-aware refusals. On three of the five handles BF16 hits, it produces a **single-digit precision error** in the secret-value suffix: `055/050`, `44/440`, `571/570`.

The third finding follows directly: at 7B on a 16K exact-match adversarial-retrieval workload, calibrated FP8 KV cache **recovers structure but loses precision**. This is invisible to partial-credit reasoning benchmarks. It is visible to exact-match retrieval.

The fourth finding follows asymmetrically: TurboQuant K8V4 at ≥4× compression matches BF16 byte-for-byte here, with no calibration step. The two compression schemes are not interchangeable in this regime.

Receipt: [`bench/vllm-fp8-vs-turboquant-2026-05-11/`](vllm-fp8-vs-turboquant-2026-05-11/) · [`FAILURE-CATALOG.md`](vllm-fp8-vs-turboquant-2026-05-11/FAILURE-CATALOG.md)

## The four findings, named

1. **Needle 5/5 at 192K context on a single 4090.** Consumer hardware fits the long context. Step one of the long-context question.
2. **Decoy 5/8 invariance across stacks, families, and model sizes.** With byte-identical wrong-answer text cross-stack. The model is downstream of the failure.
3. **Calibrated FP8 at 7B retrieval: form correct, precision off.** A regime where the "zero accuracy cost" claim breaks not by collapse but by one-digit-wrong.
4. **TurboQuant K8V4 = BF16, byte-for-byte, no calibration.** Asymmetric to FP8 in the same regime, on the same workload.

## The limit of this receipt

Every adversarial corpus tested here was **curated by the same author who built the test framework**. Eight handles, k=16 chunks each, decoys hand-crafted to be lexically dense in query terms. That is a fixture. It is reproducible. It is also synthetic.

The invariance of the 5/8 ceiling across five (stack × family × size) configurations is a property of the relationship between *this* corpus, *this* retriever, and *those* decoders. Whether the same invariance holds against a corpus the test framework did not generate — Discord captures, open-source repository text, technical PDFs about KV cache, raw user-submitted material — has not been tested. Until it is, the synthesis is:

> "This is what adversarial KV-cache retrieval looks like *when the corpus is shaped this way.*"

Not:

> "This is what adversarial KV-cache retrieval looks like *in general.*"
